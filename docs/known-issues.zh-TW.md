# 已知問題與驗證範圍

更新日期：2026-10-03，對應 v0.2.0。

## Gmail 側邊 Gemini：初步修正有效，間歇失效仍需追蹤

狀態：**已有初步有效的相容修正；全部間歇性失效的根因與長期穩定性尚未確認。** 本次原生診斷使用 V11，尚未分別驗證 V12、V13。

使用者觀察：同頁 Gmail 一般欄位正常，Gemini 有時完全不接收注音，有時漏掉部分音，例如 ㄕㄨ 只留下 ㄨ，變成「屋」。英文仍能輸入；先打英文後中文有時恢復。修正前最後一次測試「輸入測試」只出現「入測試」。

被動監看確認按鍵、焦點與欄位存在，組字占位空白約 1–2 毫秒後被移除，下一鍵重新開始組字。針對欄位的 DOM 呼叫追蹤進一步捕捉到 Gmail／Gemini 自己的清空路徑：網站的 `empty` 處理逐個呼叫 `removeChild` 移除子節點。

曾測試阻止 DOM 清空的原型，但阻止逐個 `removeChild` 會讓網站的清空迴圈無法前進，造成頁面暫時卡住。該原型已終止並撤回，**不包含在外掛內**。最終方案不攔截 DOM 刪除方法，保留正常清空迴圈。

v0.2.0 只過濾「向 Gemini 提問」欄位收到的 `isComposing=true`、`inputType=insertCompositionText`、`data=' '` 輸入通知，不取消原生編輯。中文字、英文、刪除與其他欄位的事件正常傳遞；事件委派也處理欄位重建。

套用後的原生 V11 紀錄取得七次非空白中文輸入事件，包括清空後直接輸入「輸入測試」、連續中文與換行，文字在延遲檢查中保留。使用者連續回報「現在正常」「現在都正常」。尚未向 Gemini 送出提問，驗證限於編輯器輸入。

現有證據支持「組字占位空白觸發應用程式清理，打斷組字」是本次可處理的路徑。但早期也有空白被移除後成功送入中文的反例，不能把所有失敗都視為同一原因。**其他語言介面、長時間穩定性與 V12／V13 仍待驗證。** 目前選擇器僅涵蓋繁體中文介面的「向 Gemini 提問」。

Gmail 標題僅 68 個 UTF-16 單位，沒有 V11 背景程序重新啟動的證據，與 X／Threads 的長標題當機不同。錄影最後的清空由使用者操作，不能當成網站自行刪除確認中文字的證據。

## Telegram Web K：組字空白被清空，已加入修正

狀態：**清空來源已定位，V11 空白欄位原生測試通過，v0.2.0 已包含修正。** 支援 `web.telegram.org/k/`，不涵蓋 Web A／桌面版；V12、V13 尚未個別測試。

被動監看捕捉到空白欄位收到按鍵與 compositionstart，組字空白約 6–9 毫秒後被移除；下一鍵的 isComposing=false，再度 compositionstart。使用者確認先輸入英文或數字後中文正常，清空後又失敗。

只針對該欄位的呼叫追蹤捕捉到 Telegram 自己的輸入事件處理程式呼叫 `replaceChildren()` 清空組字空白。公開 Web K 原始碼也有「把只有空白的欄位視為空內容，再清空」的路徑。欄位已有英文或數字時，便避開這條清理路徑。[Telegram 輸入欄位原始碼](https://github.com/morethanwords/tweb/blob/master/src/components/inputField.ts)

修正只在實際訊息欄位取得焦點、正在組字、內容僅有空白，且網站要清空所有子節點時，保留占位空白。確認文字、取消組字、離開欄位與一般清空仍可進行；動態新建欄位也會套用。

原生 V11 已確認四次從空白欄位直接完成「輸入測試」或「測試輸入」，不需英文或數字前綴；使用者回報恢復正常。V11 有時直接送入 insertText 而沒有 compositionend，正式腳本也處理此情況。沒有發送 Telegram 訊息。

當時標題只有 12 個 UTF-16 單位，沒有背景程序重新啟動的證據。與 Gemini 都涉及占位空白和清空路徑，但網站實作與修正方法不同，不能宣稱是同一段程式造成。

## 微軟注音為何正常？

使用者回報微軟注音正常。兩套輸入法的組字內容、事件順序或時機可能不同，使微軟注音未觸發相同的空白清理干擾。**尚未收集微軟注音的事件對照，不能把差異定為已證實。** X／Threads 的緩衝區錯誤位於自然輸入法自己的 DLL，不能套用到微軟注音。

私人對話、郵件、錄影與原始事件紀錄均不公開。外掛沒有診斷記錄功能；十五項自動化 DOM 測試不代替各版本的 Windows 原生輸入法驗證。
